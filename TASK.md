# **Тестовое задание для стажёра Backend-направления (зимняя волна 2025)**

## Магазин мерча

В Авито существует внутренний магазин мерча, где сотрудники могут приобретать товары за монеты (coin). Каждому новому сотруднику выделяется 1000 монет, которые можно использовать для покупки товаров. Кроме того, монеты можно передавать другим сотрудникам в знак благодарности или как подарок.

## Описание задачи

Необходимо реализовать сервис, который позволит сотрудникам обмениваться монетками и приобретать на них мерч. Каждый сотрудник должен иметь возможность видеть:

- Список купленных им мерчовых товаров  
- Сгруппированную информацию о перемещении монеток в его кошельке, включая:  
  - Кто ему передавал монетки и в каком количестве  
  - Кому сотрудник передавал монетки и в каком количестве

Количество монеток не может быть отрицательным, запрещено уходить в минус при операциях с монетками.

### Уведомление о покупке мерча (Kafka)

После успешной покупки мерча сотрудник должен получить email-уведомление о совершённой покупке на адрес, указанный при авторизации/регистрации.

Отправка уведомления **не должна** выполняться синхронно внутри HTTP-обработчика покупки. Вместо этого необходимо реализовать асинхронную доставку через **Apache Kafka**:

1. После успешной покупки (списание монет + запись в инвентарь) сервис публикует событие в Kafka-топик.
2. Отдельный consumer читает сообщения из топика и отправляет письмо через **реальный SMTP-сервер**.

**Подсказка (SMTP):** в `docker-compose.yaml` уже поднят Mailpit. Consumer подключается к `mailpit:1025` (енвы `SMTP_HOST` / `SMTP_PORT` / `SMTP_FROM`). Отправленные письма смотри в UI: http://localhost:8025. Из HTTP-хендлера покупки SMTP не вызывай — только publish в Kafka.

Требования к надёжности:

- Повторная обработка сообщения не должна приводить к повторной отправке одного и того же письма (at-least-once + идемпотентность на стороне consumer).
- Сбой SMTP не должен ломать HTTP-ответ успешной покупки: клиент получает `200`, а доставка уведомления происходит eventual consistency.

Минимальный состав события о покупке (можно расширить по своему усмотрению):

| Поле | Описание |
|------|----------|
| `user_id` / `username` | Покупатель |
| `email` | Адрес получателя уведомления |
| `item` | Название купленного мерча |
| `price` | Стоимость покупки в монетах |
| `purchased_at` | Время покупки |
| `event_id` | Уникальный идентификатор события (для идемпотентности) |

Формат сообщения в Kafka (JSON / Avro / Protobuf) и имя топика выбираются самостоятельно; решение нужно зафиксировать в README.

Пример тела запроса:

```json
{
  "username": "ivan",
  "password": "secret",
  "email": "ivan@example.com"
}
```

Правила:

- `email` — обязательное поле, формат должен валидироваться.
- При **первой** авторизации пользователь создаётся автоматически вместе с email.
- При **повторной** авторизации существующего пользователя, если передан другой email, сохранённый адрес **обновляется**.
- Email используется как адрес доставки уведомлений о покупке; для входа по-прежнему используются `username` + `password` и JWT.

**Мерч** — это продукт, который можно купить за монетки. Всего в магазине доступно 10 видов мерча. Каждый товар имеет уникальное название и цену. Ниже приведён список наименований и их цены.

| Название     | Цена |
|--------------|------|

| cup          | 20   |

Предполагается, что в магазине бесконечный запас каждого вида мерча.

## **Условия**

* Используйте этот API: [`schema.json`](./schema.json) / [`schema.yaml`](./schema.yaml)
* Сотрудников может быть до 100к, RPS — 1k, SLI времени ответа — 50 мс, SLI успешности ответа — 99.99%
* Для авторизации доступов должен использоваться JWT. Пользовательский токен доступа к API выдаётся после авторизации/регистрации пользователя. При первой авторизации пользователь должен создаваться автоматически вместе с email
* При повторной авторизации email из запроса обновляет сохранённый адрес пользователя
* Реализуйте покрытие бизнес сценариев юнит-тестами. Общее тестовое покрытие проекта должно превышать 40%
* Реализуйте интеграционный или E2E-тест на сценарий покупки мерча
* Реализуйте интеграционный или E2E-тест на сценарий передачи монеток другим сотрудникам
* Реализуйте интеграционный или E2E-тест на сценарий уведомления о покупке: успешная покупка → публикация в Kafka → consumer отправляет письмо через SMTP. Для проверки SMTP поднимается в Docker Compose (например Mailhog / Mailpit / GreenMail): письмо должно реально уйти по SMTP и быть доступно для проверки в тестовом окружении. API покупки (`GET /api/buy/{item}`) не меняется — уведомление является побочным эффектом

## **Требования по стеку**

**Язык сервиса:** предпочтительным является Go, но также допустимы следующие языки: PHP, Java, Python, C#.

**База данных:** рекомендуется использовать PostgreSQL, но также допустимо использовать MySQL.

**Очередь сообщений:** Apache Kafka (обязательна для сценария уведомлений о покупке).

**Почта:** реальный SMTP. В локальном/CI-окружении SMTP поднимается через Docker Compose (Mailhog / Mailpit / аналог). Параметры подключения (host, port, from, credentials при необходимости) выносятся в конфигурацию.

Для **деплоя зависимостей и самого сервиса** используйте Docker Compose. В compose должны подниматься как минимум: сервис API, БД, Kafka (и при необходимости ZooKeeper / KRaft), SMTP. Порт доступа к сервису должен быть 8080 и быть доступен снаружи как `localhost:8080`.
